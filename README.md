# GOAT Store Manager — Reseller ERP System

##  Проблема

Продавці унікального брендового одягу постійно стикаються з ризиком подвійного продажу однієї й тієї ж речі (наприклад, одночасно у фізичному роздробі та на OLX чи Shafa). Ручний облік залишків і вирахування чистого прибутку з урахуванням комісій різних маркетплейсів займає багато часу та призводить до фінансових помилок.

##  Цільова аудиторія

* Власники локальних магазинів брендового та вінтажного одягу.
* Незалежні реселери, які поєднують офлайн- та онлайн-продажі.
* Продавці-консультанти та менеджери складу.

##  Основні функції (Core Features)

1. **Управління складом:** Додавання, редагування та облік унікальних позицій (бренд, розмір, стан) з можливістю зміни статусів ("В наявності", "Брак", "Втрачено").
2. **Синхронізація наявності:** Швидке переведення товару в статус "Продано" на касі для уникнення конфліктів наявності на онлайн-вітринах.
3. **Фінанси та звіти:** Автоматичний розрахунок чистого прибутку з вирахуванням витрат на пакування, доставку та комісій платформ.
4. **Ролевий доступ:** Стандартна авторизація з розділенням прав між адміністраторами (повний доступ до фінансів) та продавцями-консультантами.

##  Склад команди та відповідальність

* **Арсен та Софія (WPF/UI):** Розробка графічного інтерфейсу (XAML), реалізація патерну проєктування MVVM, екрани складу та оформлення продажів.
* **Олексій (Backend / Core Engineer):** C#-архітектура, загальна бізнес-логіка, ViewModels, логіка авторизації та обробки статусів товарів.
* **Ігор (Data Layer Engineer):** Проєктування реляційної бази даних PostgreSQL, налаштування Entity Framework Core та міграцій.
* **Володя (QA & Test Automation):** Стратегія тестування, написання модульних тестів (xUnit), налаштування CI пайплайнів.

##  Стек технологій та процес розробки

* **Архітектура:** C#, .NET 8, WPF (MVVM).
* **База даних:** PostgreSQL (взаємодія через Entity Framework Core).
* **Управління проєктом:** GitHub Projects Kanban-дошка (Todo → In Progress → Done).
* **CI/CD:** GitHub Actions — автоматична збірка та запуск тестів на кожен Pull Request.
* **Робочий процес (Workflow):** Створення окремих Feature-гілок + обов'язкове Code Review перед злиттям у `main`.

##  Локальний запуск

### Крок 1. Отримайте рядок підключення до бази (один раз)

Наша база даних живе в Supabase. Щоб API міг до неї достукатися, йому потрібен **рядок підключення** — «адреса з ключем» до бази в одному рядку. Виглядає він так:

```
Host=<сервер>.pooler.supabase.com;Port=5432;Database=postgres;Username=<логін>;Password=<пароль>;SSL Mode=Require;Trust Server Certificate=true
```

У ньому є адреса сервера, логін і **пароль від бази**. Хто має цей рядок, той може читати, змінювати й видаляти всі наші дані. Тому в репозиторії його немає, і в спільні чати його теж не кидаємо.

Де його взяти:
- **Попросіть у того, хто керує базою** (Ігор, Data Layer) або в будь-кого з команди, у кого вже все працює. Нехай надішле **особистим повідомленням**.
- **Або візьміть самі в Supabase**, якщо маєте доступ до проєкту: кнопка **Connect** → рядок підключення для .NET → підставте пароль бази.

### Крок 2. Збережіть рядок у себе на комп'ютері (один раз)

Відкрийте термінал у корені репозиторію і виконайте команду, вставивши свій рядок замість `<рядок підключення>` (у лапках):

```bash
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "<рядок підключення>" --project GoatStore.API/GoatStore.API.Server
```

Рядок збережеться в **user-secrets** — це маленький файл із секретами у вашому профілі Windows (`%APPDATA%\Microsoft\UserSecrets\...`). Він лежить поза репозиторієм, тож у Git ніколи не потрапить, і в кожного учасника він свій. Повторювати команду треба, лише якщо зміниться пароль від бази.

Більше нічого налаштовувати не треба: ключ для підпису JWT-токенів для розробки вже лежить у `appsettings.Development.json`.

> Якщо API при старті падає з помилкою «Не задано ConnectionStrings:DefaultConnection», значить крок 2 не виконано. Перевірити, що секрет збережено: `dotnet user-secrets list --project GoatStore.API/GoatStore.API.Server`.

### Крок 3. Запуск

WPF-застосунок сам до бази не ходить — усе робить через API. Тому працювати мають обидва: і API, і WPF.

**У Visual Studio (найпростіше):** правий клік на рішенні → **Configure Startup Projects** → **Multiple startup projects** → поставте **Start** для `GoatStore.API.Server` (профіль `http`) і для `LogWindowUI` → F5. Запустяться обидва разом. API прогрівається кілька секунд: якщо одразу після запуску вхід пише «Не вдалося зв'язатися із сервером», зачекайте 2–3 секунди й спробуйте ще раз.

**З терміналу** (у двох окремих вікнах, спершу API):

```bash
dotnet run --project GoatStore.API/GoatStore.API.Server --launch-profile http
dotnet run --project LogWindowUI/LogWindowUI
```

WPF шукає API на `http://localhost:5585`. Якщо API працює на іншій адресі, задайте її змінною `GOATSTORE_API_URL`.

### Для справжнього сервера

Коли API розгортатимемо на сервері, там замість user-secrets задаються змінні середовища: `ConnectionStrings__DefaultConnection` (рядок підключення) і `Jwt__SigningKey` (власний випадковий ключ від 32 символів, **не той**, що в `appsettings.Development.json`).

# Журналювання, обробка помилок і перевірка безпеки GoatStore

Стан на 25.11.2026. Документ описує, що реалізовано, які ризики ми перевірили і що лишається відкритим.

## 1. Журналювання

**Інструмент:** Serilog (API: `Serilog.AspNetCore`, `Serilog.Sinks.File`; WPF: `Serilog`, `Serilog.Sinks.File`).

| Де | Що пишемо | Куди |
|---|---|---|
| API, кожен запит | Метод, шлях, код відповіді, час виконання (`UseSerilogRequestLogging`) | Консоль API і файл `GoatStore.API/GoatStore.API.Server/logs/api-<дата>.log` |
| API, журнал дій (`Logging/AuditLog`) | Вхід (успіх і невдача), реєстрація, створення, зміна, видалення й продаж товару, чек, повернення. Хто (id користувача), у якому магазині, результат або причина відмови | Те саме |
| API, помилки (`Errors/ApiExceptionHandler`) | Повний текст винятку зі стеком | Те саме |
| WPF (`Services/AppLog`, `BearerTokenHandler`) | Старт і завершення програми, кожен запит до API (метод, шлях, код, час), збої зв'язку, необроблені винятки | `%LOCALAPPDATA%\GoatStore\logs\wpf-<дата>.log` |

Файли щодня нові, зберігаються 14 днів. Файли журналів у Git не потрапляють (`*.log` у `.gitignore`).

**Що навмисно НЕ пишемо в журнал:**
- паролі й пароль магазину;
- токени доступу;
- повний email при невдалому вході: лише маска `o***@gmail.com`, щоб журнал не став списком логінів;
- рядок запиту в WPF (пошук може містити дані покупця), лише шлях.

Це перевіряють тести: `AuditLogTests` (API) і `AppLoggingTests` (WPF).

## 2. Обробка помилкових ситуацій

| Ситуація | Що бачить користувач | Що в журналі |
|---|---|---|
| Невірні дані (порожня назва, від'ємна ціна, знижка більша за суму тощо) | 400 і текст, що саме не так | Попередження з причиною |
| Товар або чек не знайдено, чужий магазин | 404 | Попередження |
| Товар уже продано, дубль артикула, товар змінився під час редагування | 409 і зрозуміле пояснення | Попередження |
| Немає прав (продавець відкриває звіт власника) | 403 | Запис запиту з кодом 403 |
| База даних недоступна | 503 «База даних тимчасово недоступна. Спробуйте ще раз за хвилину.» | Помилка зі стеком |
| Будь-яка інша неочікувана помилка API | 500 «На сервері сталася помилка. Спробуйте ще раз.» без технічних деталей | Помилка зі стеком |
| API не запущено або немає мережі (WPF) | Повідомлення «Помилка зв'язку з сервером» | Помилка з адресою запиту |
| Неочікувана помилка у вікні WPF | Повідомлення з шляхом до журналу, програма не закривається | Помилка зі стеком |
| Продаж кількох товарів, один уже продано | Весь чек відкочується, жоден товар не продається | Попередження «Sale not created» з причиною |

## 3. Перевірка вхідних даних
- Усі вхідні дані перевіряються в сервісах `GoatStore.Core` (`AuthService`, `ProductService`, `SaleService`), а не лише у формах WPF. Тому обійти перевірку прямим запитом до API не вийде.
- Товар: обов'язкові поля, довжини (назва до 200, бренд до 100, артикул до 50), ціни від 0 до 10 000 000, кількість від 1 до 100 000, унікальна річ лише в одному екземплярі.
- Чек: не порожній, кількість не менша за 1, знижка не від'ємна і не більша за суму, відомий спосіб оплати, товари лише свого магазину.
- Повернення: лише рядки цього чека, не більше, ніж продано, повторно той самий рядок повернути не можна.
- Реєстрація й вхід: формат email, довжина пароля, підтвердження пароля, пароль магазину.
- Покрито unit- та інтеграційними тестами (усього понад 600 тестів).

## 4. Секрети
- Рядок підключення до бази лише в user-secrets (розробка) або змінній середовища (сервер). У `appsettings.json` секретів немає. Без рядка API не стартує.
- Ключ підпису JWT на сервері задається змінною `Jwt__SigningKey`, без неї API не стартує (`ValidateOnStart`). Ключ у `appsettings.Development.json` лише для локальної розробки.
- Журнали не містять паролів, токенів і рядка підключення.

## 5. Перевірені ризики й заходи

| Ризик | Захід | Стан |
|---|---|---|
| Викрадення паролів із бази | Паролі й пароль магазину зберігаються лише як BCrypt-хеш | Закрито |
| Перебір паролів | Обмеження спроб входу й реєстрації з однієї адреси (`RateLimiter`: 10 за хвилину, у режимі розробки 100) | Закрито |
| Перевірка, чи існує email, через відповідь входу | Однакова відповідь для «немає користувача» й «невірний пароль» | Закрито |
| Доступ без входу | Усі ендпоінти товарів, чеків і звітів вимагають JWT | Закрито |
| Продавець робить дії власника | Політика `AdminOnly` на створення, зміну, видалення товару й звіти. Тест: продавець отримує 403 | Закрито |
| Доступ до даних чужого магазину | Магазин береться лише з токена (`store_id`), а не з запиту. Тести «чужий магазин» повертають 404 | Закрито |
| SQL-ін'єкції | Лише EF Core з параметрами, ручного SQL з даними користувача немає | Закрито |
| Подвійний продаж однієї речі | Продаж одним умовним запитом у транзакції, чек «все або нічого» | Закрито |
| Перезапис продажу під час редагування товару | Зміна й видалення одним умовним запитом | Закрито |
| Витік технічних деталей у відповідях | `ApiExceptionHandler` віддає лише загальний текст | Закрито |
| Паролі й токени в журналах | Не пишемо, email маскуємо, перевірено тестами | Закрито |
| Вразливі пакети в робочих проєктах | `dotnet list package --vulnerable`: у API, Core, DataAccess і WPF вразливостей немає | Закрито |
| Вразливі пакети в інструментах розробки | `GoatStore.API.AppHost` (Aspire 13.2.4: Critical і High, а також MessagePack) і `SQLitePCLRaw` 2.1.6 у тестових проєктах (High). Ці проєкти не потрапляють на сервер | **Відкрито:** оновити пакети окремим PR |
| Старий пароль бази в історії Git | Пароль прибрано з коду, але він лишився в старих комітах | **Відкрито:** власник бази має змінити пароль у Supabase |
| Токен живе 8 годин без оновлення й відкликання | Обмежений термін дії, токен лише в пам'яті WPF, на диск не пишеться | **Відкрито:** refresh-токени після захисту |
| Немає блокування акаунта після багатьох невдалих спроб | Частково закрито обмеженням частоти | **Відкрито:** блокування після захисту |
| API працює по HTTP | Лише локально (`localhost`) | **Відкрито:** HTTPS обов'язковий при розгортанні на сервері |

## 6. Як показати на захисті
1. Запустити API і WPF, увійти, продати товар, спробувати продати його ще раз.
2. Відкрити `GoatStore.API/GoatStore.API.Server/logs/api-<сьогодні>.log`: видно вхід, чек, відмову з причиною й записи запитів.
3. Увійти з невірним паролем: у журналі «Login failed for o***@...», пароля немає.
4. Відкрити `%LOCALAPPDATA%\GoatStore\logs\wpf-<сьогодні>.log`: запити WPF до API з кодами відповідей.
5. Зупинити API і натиснути «Знайти» в WPF: користувач бачить повідомлення про зв'язок, у журналі WPF помилка з адресою.
